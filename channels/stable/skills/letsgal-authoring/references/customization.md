# 用户如何特化

公共技能保持通用；用户区按用途分开：实际运行 AI 的用户主目录下 `.letsgal-authoring/preferences/user.md` 保存个人文风、命名、确认节奏等偏好，`.letsgal-authoring/plugins/<插件ID>/<版本>/SKILL.md` 保存用户独立维护的插件使用知识，工程根 `LETSGAL.md` 保存本作品约定和实际插件选择。它们都在公共技能目录外，安装／更新／卸载不会覆盖已有内容。插件资料不混入个人偏好；个人偏好也不替代插件实际参数与版本依据。详见 [用户插件 Skill](plugin-skills.md)。

旧版只有 `.letsgal-authoring/user.md` 时继续使用它；安装器不搬动、删除它，也不新建一个空白 preferences/user.md 把旧偏好遮住。两处都存在时，新位置是主要编辑入口，但须读回两份并指出冲突或尚未迁入的内容；不得静默忽略旧偏好，也不自动合并。用户明确要求迁移后，先保全两份原文，再整理并验证关键约定；保留旧文件作为备份并记录迁移事实。项目的文风、目录、命名、分支习惯和发布目标优先沿用现有说明；LETSGAL.md 可只写入口链接，不复制一份容易失效的规则。

偏好按“当前请求 → 本作品明确选择 → 个人一般偏好 → 公共默认”解释；这不是改变宿主指令优先级或安全权限。冲突涉及作品目标时说明冲突并询问用户；普通显示风格等可按具体覆盖一般处理。

需要新项目入口时参考 [LETSGAL.example.md](../templates/LETSGAL.example.md)。安装技能不自动写入真实作品，也不把示例值当作已确认偏好。

个人配置可以让不同本地 harness 共用；远程 SSH、WSL、容器和云端有自己的主目录，必须把所需配置明确复制到目标环境，不宣称本机安装已经同步。

用户可直接说：

> 按这个项目的实际情况，为 letsgal-authoring 建立项目配置。先读已有规则，保留冲突待我确认；记录我的文风、素材路径、Git 习惯和验证目标，不修改公共技能或其他工程。

只需适配一种工具时，优先修改该工具支持的用户／项目配置。可用工具、MCP 注册和权限仍由实际 harness 决定，项目说明不能凭空添加能力。

若用户明确要求改技能本身，先备份当前版本，并记录为本地修改；更新安装器应检测到差异而不是覆盖。长期分叉可换独立名称并保留来源说明；同名公共版与私有版同时安装可能造成加载歧义。不要为了“同步”自动改动其他 harness 的副本。

旧版特调迁移：比较原 Skill、安装时的文件指纹与新包，把个人习惯整理到 user.md、作品选择整理到 LETSGAL.md，通用修正另提候选补丁。读回配置并确认关键信息保留后再替换公共文件，原版本仍存备份。无法判断的段落保留并让用户决定；不自动总结后删除原文。

可定制项目：语言与文风、确认节奏、命名、素材布局、备份目录、Git 分支及提交习惯、适用平台、测试深度、交接文件。应写入具体选择，未决定项保持未定，不默默代填。
