# 协作与 Git

## 人与 AI 如何分工

用户负责目标与重要创作取舍；AI 将目标拆成能审阅的小批内容和改动。不强制每个步骤确认，也不把未讨论的剧情提案直接变成世界设定。

多人或多个 AI 的任务应写明：目标、允许修改的文件／章节、共享接口、不得触及的范围、验收点、交接位置。同一 JSON 同一时间只安排一个写入者；`project.json`、角色／变量表等共享文件指定整合者。可以并行准备素材和草案，最后由整合者核 ID、引用及路线。只有用户或所在环境允许时才启动额外代理，不因技能存在就自行开多个收费会话。

Studio 实时协作有章节编辑权和同步冲突机制；外部文件编辑不应被假定遵守该锁。持有其他人编辑权的章节先暂停写入。选择云端覆盖可能丢弃本地未同步内容，应先保全并明确冲突处理。细节见 [官方协作说明](https://docs.avg-engine.com/manual/overview/collaboration)。

## Git 开始前

在确认的工程目录运行以下只读检查；不是仓库时停止 Git 步骤，不在父目录建立跨作品总库：

```sh
git rev-parse --show-toplevel
git status --short --branch
git diff --stat
git diff --cached --stat
```

看清分支、已暂存、未暂存和未跟踪内容；不将用户原有变化算作本次成果。仓库存在不代表素材完整入库或远端已有备份。未建立 Git 的项目，先提出独立仓库和忽略规则方案，按授权初始化；不擅自联网创建仓库。

## 开发与提交

默认沿用工程的分支、提交频率和素材策略。需要并行隔离且用户／环境已允许时可用独立分支或 worktree；worktree 不自动携带原目录未提交内容，也不是大型素材备份。先核工作目录与引擎关联路径，再打开目标副本。[Git worktree](https://git-scm.com/docs/git-worktree)

只暂存本次确定的路径，例如 `git add -- "chapters/本次章节.json"`，随后审查 `git diff --cached -- <路径>`。若用户已有暂存内容，避免一次 commit 把它们混入；使用经核实的路径限定提交方式或协调索引，不擅自 unstage/stash 他人工作。提交行为沿项目约定和当前授权；push、force-push、重写公共历史另判范围。

小批提交应围绕能说明的行为变化，正文和结构的大改可分开审阅。素材是否使用 Git LFS、是否提交发行物等由项目决定；不自动安装 LFS、不追溯改写历史。秘密、缓存、依赖目录的忽略规则先检查已有约定。项目内安装 Skill 时，`.letsgal-authoring-backups/` 中可能有私有特调；提交前核对排除范围，不把整个备份目录打进作品仓库。

## 冲突与恢复

JSON 冲突按结构合并，保留双方目标与稳定 ID。不能只删除冲突标记或整文件选 ours/theirs 就称解决；重查章节索引、变量消费者、分支和素材引用，并做相关预览。

回退前先保全当前工作。查明目标 commit 与路径；优先把旧内容取到另一个文件比较，不直接覆盖原文。`git restore` 默认会改写工作区，选项还可能影响索引，执行前须明确源版本和路径。[Git restore](https://git-scm.com/docs/git-restore)

## 交接

复用项目既有状态文件。没有时可用一小份记录：当前目标、已确认决定、改动路径、分支／提交、已通过的验证、未验证项、已知问题、下一步和仍运行的编辑器／构建进程。详细过程另存；不要把整个聊天变成必读入口。
